Workforce Management is a Supporting bounded context that owns "who is on
shift, on which process path, at what rate; direct vs indirect hours."

It covers two things:

1. **The shift-start planning horizon** — a human proposes and then
   commits a split of headcount across process paths (`ShiftPlan`, made
   of `PathPlan` lines: path, planned heads, planned rate, planned
   hours), one plan per building per shift.
2. **Intra-shift assignment tracking** — moving associates between paths
   as backlogs deviate from plan (`LaborAssignment`). The move itself is
   always a human call; this context makes the staffing gap legible
   (`GetStaffingGap` / `PathUnderstaffed`), it never decides or performs
   a rebalance on its own.

Three aggregates back the API: `AssociateShift` (roster entry —
certifications, break state, logged hours), `ShiftPlan` (committed
headcount split across paths), and `LaborAssignment` (one associate, one
path, an interval — exactly one ACTIVE assignment per associate at a
time, and an assignment is rejected if the associate lacks the path's
required certification).

**Where this context's boundary stops:** it never links an associate to
a specific task, and it never dispatches work — that is Fulfillment
Execution's job, against a completely different cadence (shifts/hours
here vs. seconds there for task claiming). Keeping the seam at "this
associate is on this path" lets task-dispatch policy change without
touching workforce planning, and vice versa.

All error responses use RFC 7807 (`application/problem+json`); see the
shared `Problem` schema.
