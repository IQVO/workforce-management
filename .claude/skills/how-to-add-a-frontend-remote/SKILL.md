# How to add a frontend remote

Use when adding a new screen/feature to this repo's `web/` Module
Federation remote (`workforce-mfe`). This is the Vite/React micro-frontend
layer that `warehouse-console` (the shell) lazy-loads at `/workforce/*` —
see that repo's `.claude/rules/frontend.md` for the shell-side half of
this contract. `workforce-mfe` already exists and is deployed (chart
`frontend.enabled`, its own nginx workload — see
`docs/docs/adr/0011-adopt-fleet-mfe-console-architecture.md`); this guide
covers extending it, not standing one up from nothing.

## `web/vite.config.ts` must stay in OBJECT form, always

This repo's real config already follows the rule, and its own comment
explains why — read it before touching this file:

```ts
// Kept as a plain object rather than the ({ command }) => ({...}) callback
// form on purpose: vitest.config.ts does mergeConfig(viteConfig, ...) and Vite
// throws "Cannot merge config in form of callback" on a function export, which
// breaks the whole test suite. Reading the command off process.argv keeps this
// a static object.
const IS_BUILD = process.argv.includes("build");
const PUBLIC_BASE = IS_BUILD ? "/mfes/workforce-management/" : "/";

export default defineConfig({
  base: PUBLIC_BASE,
  // ... federation plugin config, etc.
});
```

Never convert this to the callback form
(`defineConfig(({ command }) => ({...}))`) to compute `base` dynamically
or for any other reason — `web/vitest.config.ts` does
`mergeConfig(viteConfig, defineConfig({...}))`, and Vite throws on a
function export, killing the ENTIRE test suite for a one-line config
change.

## A tiny, relative `dist/remoteEntry.js` after build is CORRECT

After `npm run build` with the `/mfes/workforce-management/` base,
`dist/remoteEntry.js` is a small relative re-export
(`./assets/virtual_mf-REMOTE_ENTRY_ID...js`) — grepping it for
`/mfes/workforce-management/` returns zero matches. That is expected, not
a bug: `dist/index.html` carries the absolute prefixed URLs, every JS
chunk uses relative ESM imports, and the module-preload helper resolves
origin-relative to wherever `remoteEntry.js` was actually fetched from —
exactly what a path-mounted remote needs. Verify correctness by serving
the built image and fetching through the real gateway path (the split
localhost edge: Nginx on `:80` for `/mfes/workforce-management/`, Kong on
`:8000` for the REST API — they never proxy to each other), never by
grepping the built file for the expected prefix.

## `@warehouse/ui-kit` is a sibling checkout, not a registry package

`web/package.json` depends on it via `"@warehouse/ui-kit": "file:../../warehouse-ui-kit"`.
Any domain-status color, chart, or shared layout primitive belongs in
that repo, not hand-rolled here — a remote reinventing its own palette
instead of consuming the shared kit's components is a bug, not a style
choice (visual consistency across the MFE boundary is the #1 place MFE
UX fails).

## The `test` script already exists here — keep it that way

`web/package.json`'s `"test": "vitest run"` is already wired (unlike
several other remotes in this fleet, which historically shipped only
build/dev/lint/preview and silently never ran an added `*.test.ts`
file). `web/src/config.test.ts` is the existing example — a pure
resolver test with a `window === "undefined"` guard in `config.ts` so it
is unit-testable without jsdom. Confirm any new test file is actually
picked up by running `npm test` locally, and confirm CI's `web` job
(`.github/workflows/ci.yml`, added in PR #68) still invokes it, not just
`npm run build`.

## The Docker build recipe (packaging as a deployable nginx workload)

`web/Dockerfile` already implements the three traps below, heavily
commented — copy its structure for any change, rather than re-deriving
them from scratch:

1. **Base image must be `node:22-bookworm-slim`, not alpine or a newer
   node image.** `web/package-lock.json` was generated by npm 10 and
   carries no Linux entries for Vite's platform-specific optional
   dependencies (`@rolldown/binding-linux-*`, `lightningcss-linux-*`,
   `@oxlint/binding-linux-*`). npm 11 (node:26) rejects that lockfile
   outright with `EUSAGE "lock file out of sync"`; Debian/glibc matches
   the published `*-gnu` bindings npm/cli#4828's workaround needs.
2. **Do NOT install from the committed lockfile.** `npm/cli#4828` means
   even a successful `npm ci` against this lockfile leaves the native
   binding missing on Linux. The working recipe, straight from this
   repo's Dockerfile: `rm -f package-lock.json` then
   `npm install --no-save` (build-stage only; the committed lockfile is
   never mutated). The ui-kit build stage does the same, plus
   `rm -rf node_modules` first, since it arrives as a named BuildKit
   context from a developer checkout that may carry host-platform
   bindings.
3. **`@warehouse/ui-kit` must be supplied as a named BuildKit context**:
   ```bash
   docker build --build-context uikit=../../warehouse-ui-kit \
     -t warehouse/workforce-management-frontend:local .
   ```

## Wiring into the deploy

A new remote screen inside the existing `workforce-mfe` doesn't need new
deploy wiring — it ships in the same image/chart. Standing up a BRAND
NEW remote for a bounded context that doesn't have one yet is a bigger
change: `warehouse-infra`'s `local.services` map and this repo's own
Helm chart (`frontend.enabled` value) both need updating — see
`warehouse-infra`'s AGENTS.md for the Terraform side.

**This repo's chart requires a database URL to render.** Any `helm
template` invocation against `charts/workforce-management` fails with
"requires database.url or database.existingSecret" without one — pass a
dummy value in any local chart-render check:
`--set database.url=postgres://u:p@example.invalid:5432/db`. This is
unrelated to the frontend specifically (every workload in the chart is
gated on the same values file), but it is the single most common reason
a `helm template` smoke-test of this repo's chart fails for someone
touching the `web/` remote for the first time.

## Key commands

```bash
cd web
npm ci
npm run lint        # oxlint
npx tsc -b           # typecheck
npm test             # vitest run — confirm this actually runs your new test
npm run build         # tsc -b && vite build -> dist/
```

CI's `web` job (`.github/workflows/ci.yml`) runs this exact sequence
against a dual checkout — it checks out this repo into
`workforce-management/`, checks out `IQVO/warehouse-ui-kit@develop`
into a sibling `warehouse-ui-kit/` directory, builds the ui-kit first
(`npm ci && npm run build`), then runs this repo's `web/` steps.
Reproduce that locally by checking out `warehouse-ui-kit` as a real
sibling directory if `npm ci` behaves differently than CI.
